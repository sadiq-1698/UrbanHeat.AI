# ml

Python tooling for the heat model: per-cell **feature engineering** and the **training table** (Session 13), then XGBoost / Random Forest
training and ONNX export (Session 14). Artifacts land in `ml/artifacts/` (binaries gitignored).

```bash
cd ml
python3 -m virtualenv .venv && .venv/bin/pip install -r requirements.txt     # or python3 -m venv
.venv/bin/python -W ignore -m unittest discover -s tests -t .                # 29 tests
.venv/bin/python -m urbanheat_ml.build_dataset --region demo-city            # -> ../data/ml/demo-city/dataset.csv.gz + dataset.meta.json
```

Needs the region's rasters and land cover from `db/ingest` (`data/rasters/<region>-{canopy,impervious,elevation,lst}.tif` on one grid,
and `data/<region>/landcover.geojson`). Works the same for the demo city and for real regions ingested with `real_data.ingest`.

## What is being predicted

**Target: `lst_anomaly_c`** = land surface temperature minus a vegetated reference baseline, i.e. how many °C hotter than a cool, green, unpaved
cell this cell runs: the "temperature spike". The baseline is the median LST of reference cells (canopy ≥ 60 %, impervious ≤ 5 %, not water);
if fewer than 30 such cells exist it falls back to the 10th percentile of land LST and says so in the metadata. The anomaly is what the model
learns (a hot day shifts every temperature, the anomaly is what land cover explains); `lst_c` is kept alongside it. Open-water cells are excluded by
default (their physics differs; `--include-water` keeps them, flagged).

## Features (12)

The specification is the docstring of [`urbanheat_ml/features.py`](urbanheat_ml/features.py); the TypeScript port in `packages/geo-core/src/features.ts`
follows it exactly. Neighbourhood statistics use a rectangular window sized from a ground radius (so the same radius means the same thing at 30 m or 90 m
cells), clipped at the grid edge, averaging only valid cells.

| Feature | Meaning |
|---|---|
| `canopy_pct`, `impervious_pct` | the cell's own cover |
| `canopy_mean_{150,500,1000}m`, `impervious_mean_{150,500,1000}m` | mean cover in the surrounding window, **land cells only** (water has canopy = impervious = 0, which would read as "bare ground") |
| `elevation_m`, `elev_rel_1000m` | elevation, and elevation minus its 1 km window mean (local relief) |
| `dist_water_m` | Euclidean distance to the nearest water cell (exact, anisotropic), capped at 5 000 m |
| `water_frac_500m` | share of the 500 m window that is water (the cooling halo) |

**Deliberately not features:** longitude, latitude, row, column. They would let a model memorise places and would not transfer to another city. They are
kept as columns (with `block_id` and `fold`) for spatial cross-validation only; a test asserts none of them is in `FEATURE_NAMES`.

## Spatial cross-validation

Adjacent cells are almost identical, so a random train/test split leaks and flatters any model. Cells are grouped into square **blocks** (default 2 km),
the blocks are shuffled with a seed and dealt into **5 folds**, so a held-out fold is whole regions the model never saw nearby. Verified: no block ever
spans two folds; folds are deterministic per seed. On the demo city: 72 blocks, 7.5–8.9 k rows per fold.

## Output

`dataset.csv.gz`: `row, col, lon, lat, block_id, fold, <12 features>, is_water, lst_c, lst_anomaly_c`. `dataset.meta.json`: grid and cell sizes, the feature
list (the model's input order), radii, distance cap, baseline and how it was chosen, cell counts (total / water / dropped-incomplete / kept), and the CV setup.
Cells with any missing input are dropped and counted. The demo city yields **40 266 rows** (43 200 cells, 2 934 water, 0 incomplete), 1.8 MB.

## Python and TypeScript must agree

Training happens here; inference (and the scenario simulator, which edits canopy/impervious and recomputes neighbourhoods) runs in Node. A feature that
differs by a rounding rule would silently degrade every prediction, so parity is tested three ways:

1. A **golden fixture** (`packages/geo-core/test-fixtures/features-golden.json`, generated by `python -m urbanheat_ml.golden`: seeded scene with NaN
   inputs, irregular water, anisotropic cells) is verified by *both* suites: `ml/tests/test_golden.py` recomputes it from the stored inputs and
   `packages/geo-core/src/features-golden.test.ts` checks the TypeScript output against it to 1e-9. Changing `features.py` fails the first until the fixture
   is regenerated, and the second then checks the port. (Checked that it can fail: making the TS port include water in the canopy means is caught at once.)
2. Brute-force unit tests in both languages for window means, the distance transform (including anisotropic cells), and the stack.
3. **End to end on real data**: Node computed all 12 features from the demo rasters and polygons and compared them with every one of the 40 266 rows of the
   Python dataset: the same 2 934 water cells, and every feature within the CSV's 5-significant-digit rounding. Node builds the full stack for 43 200 cells in ~30 ms.

## What the demo data says (and doesn't)

On the demo city the features behave physically: correlation with the anomaly is +0.95 for `impervious_pct` and −0.93 for `canopy_pct`; cells within 200 m of
water average +0.9 °C against +2.0 °C beyond 1.5 km; 22.5 % of land cells are more than 3 °C above the baseline.

Caveats to carry into Session 14: **the demo LST is synthetic and was generated from impervious cover, canopy, elevation and water proximity**, so these
correlations are by construction, and a model will look better here than on real data. The smooth synthetic fields also make a cell's own canopy and its
150 m mean almost the same number (r = 1.00), so the neighbourhood features are largely redundant on this data; real, patchier land cover should differ.
Elevation barely matters (the generator's lapse term is small). None of this is evidence about a real city; Session 20 repeats it on real data.
